# 0020 - libwol: one app API behind a stable C ABI
Status: accepted. Builds on 0010 (widgets), 0015 (security defaults).
Context: apps need one native way to use the Kit and the system's services, from any language (Rust now; Swift, Crystal, .NET languages later), and an app built today must still run years from now. Rust has no stable ABI; a C ABI is the one every language can call.
Decision:
- Boundary: `libwol.so.1` and `wol.h` (`crates/wol-abi`). Rust behind it, C at the edge. Handles are opaque (no struct layout is public). No Rust type crosses. Strings are UTF-8 with a length. Every call that can fail returns a `wol_status` and, if asked, a `wol_error` object with a sentence to show. Callbacks take `void *user_data`.
- Ownership (CoreFoundation's rule): `_create` and `_copy` return a reference the caller releases; `_get_` borrows from its argument; `_retain`/`_release` count references; release accepts NULL.
- Threads: retain/release from any thread; everything else on a context from one thread at a time. Callbacks run only inside `wol_context_dispatch`, on the calling thread. The context's fd turns readable when something waits, so any event loop (GLib, libdispatch, a language runtime) can drive libwol. Events and subscriptions are part of the core, not an add-on.
- Stability: symbols carry versions from `abi/wol.map` (WOL_1.0, then WOL_1.1, ...). A shipped symbol or declaration never changes or goes away; new ones are added in a new node. `tests/abi.rs` fails on any removal or change: exported symbols against `abi/wol-*.symbols`, the header against the `abi/wol-1.0.h` snapshot, and the header against the Rust exports and constants. The soname is the major version. The library is linked from the staticlib by `link.sh`, so the map alone decides what is exported.
- Security: libwol holds no privilege and no ambient authority. Reading the person's own settings (appearance, accent) happens in the app; anything done for the app is a call to wold (`shared::portal`, one JSON line on the wold socket). wold takes the caller's identity from the kernel (peer uid, executable of the peer pid), never from the message, and checks the grant in the consent database the person controls in Settings > Privacy & Security (`notifications` is the first). Each call names one capability; fields are bounded and checked on both sides; decoders are fuzzed (`shared/tests/portal_fuzz.rs`, `fuzz/`). A notification reaches only its account's notification shower (the shell, admitted by executable through `subscribe account`); apps can neither read nor forge one. Panics stop at the boundary.
- The person stays in charge: no telemetry and no calls the person cannot see. libwol opens only the wold socket and the Kit host socket; nothing goes to the network. Every grant is a line in a readable file, listed in Settings, and can be turned off; a denial says where to change it.
- Licensing: libwol and `wol.h` are BSD-2-Clause, usable by apps of any license. The Kit stays in the GPL shell and is not linked into apps: an app sends a view tree as data (`shared::view`, BSD) to the Kit host (the shell) over a socket, the host draws it with Kit parts and sends clicks back. Apps get the Kit's look and behaviour without linking it.
- Widgets in Lua (`crates/wol-lua`): a desktop widget is one `.lua` file returning `wol.widget { name, refresh, permissions, render }`; `render` builds the same view tree. Lua 5.4 (vendored, MIT) runs with string, table, math and utf8 only: no io, os, require, debug, loaders or bytecode; 16 MiB and an instruction budget per call. Services exist only for declared permissions and only after the file has loaded; wold still checks each call. `~/.config/wolos/widgets/` reloads on change.
Consequences: the Kit host (shell side) and the shell showing wold notifications come next; until then a window or a notification answers `WOL_ERR_UNAVAILABLE`. The caller's identity is its executable when wold reads it (pidfd later); an interpreter's grant covers every script it runs. A view tree is coarser than a toolkit: new Kit parts are added to `shared::view` and to the header together.
