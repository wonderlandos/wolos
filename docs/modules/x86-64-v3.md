# x86-64-v3 for our own packages (ADR 0030)

Evaluated 2026-11-04 (IMAGE-F). Lead order: evaluate building `wolos-*`, `hyprland-wolos` and `rsh` with `-march=x86-64-v3` in the forge build, measure size and speed on three binaries, add the install-time guard and a `wol doctor` row, keep baseline packages where "everything functional" needs them, and say which: v3 builds with a fallback repo, or v3 only with the installer guard.

Decision records: ADR 0019 and 0030 (the CPU gate for the CachyOS v3 repos and `linux-wolos-v3`). Code: `wol_core::mirror` (`x86_64_level`, `cachy_supported`, `kernel_package`), `wol mirror status|gate|kernel`, `wolos-build pkg --march` (wolos-build `lib/pkg.sh`), `files/usr/lib/wolos/install-run` (the guard), `wol doctor hardware` row `cpu-level` ([doctor.md](doctor.md)).

## Recommendation

**Baseline stays the default; v3 is an additive, gated flavour; never v3 only.**

1. **Never v3 only.** x86-64-v3 needs AVX2, BMI1/2, FMA, F16C, MOVBE (Haswell 2013 and Zen 1 / Excavator 2015 and newer). The Intel Atom-class cores (Apollo Lake, Gemini Lake, Jasper Lake: Celeron N3xxx to N5xxx, Pentium Silver), several Pentium/Celeron Gold generations, and the default CPU model of QEMU (`qemu64`) have no AVX2. Those are the cheap laptops and the test VMs. A v3-only image would stop with "illegal instruction" there, which breaks the rule that everything functions. The guard below would then have to refuse them; with a baseline it does not need to.
2. **Where v3 earns its place, ship it as a second repo, `[wolos-v3]`, ahead of `[wolos]`, turned on by the same gate as the CachyOS repos** (`wol mirror gate`: AVX2 present, section on; else off). Packages carry `arch = x86_64_v3` (`CARCH=x86_64_v3`, pacman has `Architecture = x86_64 x86_64_v3` since ADR 0030). The baseline repo never changes, so the fallback is the repo that exists today. A disk moved to an older computer is re-gated on the next boot (`wolos-firstboot`), and `wol doctor hardware` row `cpu-level` fails loudly if the optimized sections are on while the processor lacks AVX2.
3. **Not yet.** The measured gain of our binaries is small (below), so the second repo costs more than it returns today: a second build, a second database, a second CDN path and a second thing to bisect. What this change delivers is the part that has to exist first and is cheap to keep: the build flavour (`wolos-build pkg --march v3`), the opt-out list (`march.skip`), the guard and the doctor row. Turning the repo on is a one-line decision per package list once a package measures well: `rsh` is the first candidate (text matching, below); the compositor (`hyprland-wolos`) is the one that could matter most and could not be measured here (it needs the GPU session).

## Measurements

Forge (Intel Xeon Platinum 8375C, Ice Lake, 128 vCPU, shared: load average 70 to 130 during the runs, so every speed is the minimum CPU time (user + system) of N runs, which is the least noisy number a loaded box gives). Baseline = what Arch's `makepkg.conf` gives (`-march=x86-64 -mtune=generic`, no `target-cpu`); v3 = `-march=x86-64-v3` / `-C target-cpu=x86-64-v3` (Crystal: `--mcpu x86-64-v3`). Same sources, same flags otherwise. Scripts: `.claude/tmp/imagef-bench/march-bench*.sh`, results `/scratch/imagef/out/` on the forge.

| Binary (language) | Size, baseline -> v3 | Work measured | CPU time, baseline -> v3 |
|---|---|---|---|
| `wol-xguard` (Rust, YARA-X + hashing + decompression) | 30,896,512 -> 31,102,576 B (+0.7%) | `scan` of 600 files from `/usr/lib` and `/usr/bin`, rules built once, 5 runs | 2.20 s -> 2.18 s (-0.9%) |
| `wol` (Rust, controller CLI) | 7,954,456 -> 7,973,832 B (+0.2%) | 300 starts of `wol mirror status --json`, 5 runs | 1.80 s -> 1.83 s (+1.7%, noise) |
| `wol-hue` (Crystal, palette from a picture) | 1,409,200 -> 1,411,768 B (+0.2%) | the repo's 50 megapixel JPEG, 7 runs | 0.320 s -> 0.320 s (0%) |
| `rsh` 0.9.1 (C++ with mruby, `-Os` recipe) | 1,253,592 -> 1,253,592 B (0%) | `1M x =~ with $1`, scan of a 1 MB text, 100,000-line `readlines =~`; 15 runs | 1.91 -> 1.85 s (-3%); 0.09 -> 0.08 s; 0.40 -> 0.30 s (-25%) |

What it says:

- **Size** grows by 0 to 0.7%. v3 code is not smaller; AVX2 instructions are longer.
- **Speed** moves by about the noise for the Rust and Crystal programs. The reasons are in the programs: the hot loops that benefit from AVX2 (hashing, `memchr`, `aho-corasick`, zstd) already pick their implementation at run time (`cpufeatures`, `is_x86_feature_detected!`, the system's libzstd), so a baseline build already runs them at full speed on an AVX2 CPU; `wol` is startup-bound; `wol-hue`'s time is the JPEG decoder in the system's libjpeg. Only 17 `ymm` instructions appear in the v3 `rsh` against 0 in the baseline: the compiler found little to vectorize.
- **`rsh`'s text matching** is the one clear gain (-25% on matching lines of a 100,000-line file, repeated in two runs; the others are within 3%). It reaches that only after one recipe fix, below.
- Not measured: `hyprland-wolos` (the compositor; its cost is per frame, needs the GPU session and the frame-time harness), `wol-shell` and the GTK programs (the time is in GTK, Cairo and Mesa, which are Arch's builds), `wopkg`/`libwol` (library code; same reason as `wol-xguard`).

## What had to be found out to build v3 at all

- **makepkg's `CFLAGS` do not reach everything.** `rsh`'s own C++ takes `CXXFLAGS` from the environment (its Makefile appends with `+=`; passed on the `make` command line it is ignored and the build fails), but the mruby interpreter inside it is built by a Ruby build script with its own hard-coded `conf.cc.flags` (`build_config.rb`): the hot half, the VM, stays baseline unless the recipe patches that line. Crystal ignores `CFLAGS` altogether (`--mcpu` is on the `crystal build` line). A v3 flavour is therefore per recipe, not just a makepkg.conf change; `march.skip` lists the recipes the flavour must not touch.
- **`arch=(x86_64)` refuses `CARCH=x86_64_v3`** ("not available for the architecture"): the flavour passes `-A`. The package file is named `...-x86_64_v3.pkg.tar.zst` and its `.PKGINFO` says `arch = x86_64_v3`, which pacman accepts with `Architecture = x86_64 x86_64_v3` and which cannot be mistaken for a baseline file in the baseline repo.
