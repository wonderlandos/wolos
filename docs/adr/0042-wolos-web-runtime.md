# 0042 - A WolOS web-app runtime on the Rust browser engine
Status: accepted (lead decision 2026-11-03). Track 1's profiles land with WA-4; track 2's engine and its adaptor land with WA-2 (section "The engine"). Builds on 0026 (Memory Saver), 0031 (web apps as apps), 0036 and 0039 (Crystal userland, libWolkit).

## Context
Every major platform turns web apps into apps with its own runtime. On WolOS today each web-based app ships its own embedded engine, and the browser opens site-as-app windows. The system's only levers are the Memory Saver (ADR 0026: cgroup reclaim and `process_madvise(MADV_PAGEOUT)` of background apps, no change to the apps' code) and two lines of tuning: the platform hint in `electron-flags.conf` and `code-flags.conf`, and the browser's managed policy file. That treats a symptom: dozens of engine copies, no shared cache, foreign window chrome, dialogs and notifications, and no policy layer the system owns.

## Decision
Two tracks, both kept.

Track 1, apps that bundle their own engine (packaged apps, the code editor, the browser): they stay as packaged, keep the Memory Saver, and get a per-account runtime profile.
- Profiles: Balanced (default), Light, Full, one word in `$XDG_CONFIG_HOME/wolos/web-runtime` (`wol_core::webruntime::PROFILE_FILE`). Full adds no caps and no throttling; Light never rasterises on the GPU.
- One table, `crates/core/src/webruntime.rs` `ROWS`: every switch or policy is a row with a role (shared-engine apps, code editor, browser), the profiles it is in, whether it needs a real GPU, a reason and a status. Only `Baseline` rows (shipped for correctness before this record) and `Measured` rows (a gain from the web-app benchmark, `tools/bench/webapps`, with the path of the record) reach a file. `Candidate` rows are tested but never emitted. The table covers heap caps per role, background throttling and timer alignment, tab discard for the browser, and GPU rasterisation with zero-copy upload.
- The files: generated per profile and GPU tier into `/usr/share/wolos/webruntime/<profile>-<soft|gpu>/{electron,code,helium}-flags.conf`; the browser's policies merge into its managed policy file (system-wide, so a policy row has one value for every profile). At session start wol-session picks the tier (a render node, not a VM adapter the compositor rejects, and `wol hw compute` naming a backend other than `cpu`) and `webruntime/link.sh` links each file the account does not own: missing, or a link into `/usr/share/wolos`. A file of the user's own is never touched.
- File rules, tested: the engine keeps only the last occurrence of a switch, so list switches are merged into one; launchers read the file either line by line or word-split, so every line is one word; the browser never gets a feature list from the profile (it would replace the launcher's video-decode features). The engine's compiled-code cache and snapshot data stay in the app's profile directory: no row may move or disable a cache (`webruntime::FORBIDDEN`).
- The Memory Saver learns one fact, `runtime_discarded` (`memsaver::app::Facts`): when the app's own runtime has already given its background content back, the saver goes to Saving without its own reclaim pass; App Nap and Restore are unchanged.

Track 2, WolOS's own web apps and user-created site-as-app entries: one runtime of WolOS's own on the Rust browser engine (its dependency identifier is in `docs/THIRD-PARTY.md`), not on an embedding of either of the two established C++ engines.
- One host process per app id (`wol-webhost <manifest>`), each in its own systemd scope, so the Memory Saver and the frontmost QoS see the app as one; each app is a Wolkit host window (native chrome, dialogs, notifications, theme) over a surface the engine paints, through libWolkit's native backend. Engine state shared across apps (caches) is a later record, if the benchmark shows it pays.
- Track 1's table becomes the runtime's per-app policy layer: telemetry off, jank fixes, heap limits, background throttling, declared per app and testable.
- Web apps install from the Store as manifests (URL, permissions, policies, icon), never as bundled browsers.
- Every step is gated by the web-app benchmark harness (`tools/bench/webapps`): memory, startup, frame time and idle wakeups, against the baseline of today's apps and against a Wolkit native app.

## The engine (track 2)
CTO decisions of 2026-11-03 and what the spike on the forge established:
- **Pinned by commit, built once.** The Rust browser engine at tag v0.7.0, commit `aac43a3f31a259f04a574f5ec4e959c943ad7cc7`, MPL-2.0 at the pin (`deny.toml` allows it, `docs/THIRD-PARTY.md` names it). It builds on the forge with the Arch toolchain (rust 1.99.1, clang 23; the engine asks for 1.97.1) in under seven minutes on 128 cores and renders a local page headless to a PNG. The `[wolos]` package `webengine-wolos` builds it once per pin from a checksummed tarball (cargo cannot list a package's files from the engine's git index, so the build never runs in a checkout of it), with the engine's prebuilt JavaScript engine as a checksummed file.
- **One thin C boundary.** Rust has no stable ABI, so "apps link it" means a C library: `libwolwebengine.so.1` (ABI 1, `crates/webengine/engine/include/wolwebengine.h`, 16 exports with the symbol versions of `crates/webengine/engine/wolwebengine.map`). Its shim is built as a member of the engine's own workspace, so the engine's `Cargo.lock` decides every version (the recipe refuses any other change to it), and linked from a staticlib by `crates/webengine/engine/link.sh` like libwolkit, because a cdylib would export every C symbol of the engine's dependencies. `crates/webengine` (BSD-2-Clause, depending on `shared`, `core` and `wolkit` only) loads it at run time (`libloading`): the WolOS workspace never compiles the engine and its lock never lists the engine's crates.
- **The system's decisions stay in plain Rust, tested without the engine.** The frozen `webengine::Policy` (origins, heap cap, telemetry refused, background throttle, features; WA-4 produces it), the origin gate (every navigation and every resource load is asked; nothing outside the policy's origins, `file:` only inside a folder the policy names and never the profile directory), the profile directory as the engine's only place for files, the scope name, and the input bridge from wolkit's event records.
- **Process model (amends the plan's frozen "one content process per app id").** One app is one systemd scope and one host process (`wol-webhost`, scope `app-wol-<app id>-<pid>.scope`). Inside that scope the engine runs its content processes, one per registrable domain of the app's frames (each `file:` document counts as its own; a page whose frames are one site has exactly one), each a child started as `<host> --content-process TOKEN`. The Memory Saver and the frontmost QoS act on the scope, so they see the app as one whatever its number of content processes.
- **Sandbox (amended 2026-11-03, FIX-websandbox).** The engine's own content sandbox does not load a page at the pin (it forks its jail from a multi-threaded host, needs an unprivileged user namespace and a chroot, kills the child on a 2015 allowlist of 21 system calls and never reaps it, so the host waits) and stays off (`opts.sandbox = false`). The content process confines itself instead, in `wwe_run_content_process` before the engine reads anything or starts a thread (`crates/webengine/src/engine/confine.rs`): `no_new_privs`; a Landlock ruleset (files read-only and only the system's: `/usr`, the fonts, a few files of `/etc`, the process's own `/proc` and the CPU and cgroup facts of `/sys`; no home, no profile directory (it is the host's, the content process has no storage), no `/tmp`, nothing writable but `/dev/null`; no TCP bind or connect; no signal and no abstract unix socket outside the process; and with Landlock `RESOLVE_UNIX` the only pathname unix socket it can connect to is the engine's IPC bootstrap socket, the directory of the token); and a seccomp filter (`socket` and `socketpair` for `AF_UNIX` only, so the page's network goes through the host; no `execve`, `ptrace`, mount, namespace, `bpf`, `io_uring`, `perf_event_open`, key ring, module or reboot call; a `clone` that asks for a namespace is refused). The host sets `WWE_SANDBOX` with `WWE_MULTIPROCESS` (`view::engine_flags`); the library refuses one without the other and runs the same check as `wwe_engine_new` (`confine::preflight`), so a machine that cannot confine fails with an error and not with a content process that dies while the host waits. It fails closed: Landlock ABI 6 (Linux 6.12) or newer, an architecture with a filter table (x86-64 and AArch64), every rule added and the filter installed, or the content process prints why and returns without running the page. One gap is accepted and logged: below `RESOLVE_UNIX` (Landlock ABI 9) a pathname unix socket of the user (the session bus, the manager's private socket) is reachable from the content process; `confine::REQUIRE_UNIX_RESOLVE` turns that into a refusal. `systemd-run --scope` could not carry the equivalent: it accepts the cgroup properties of the app scope and refuses `ProtectHome`, `SystemCallFilter` and `NoNewPrivileges` (execution properties belong to services). The app's scope, the origin gate and the profile directory remain the bounds on the host process.
- **Where the pin misbehaves, and the answer.** Denying a frame's first navigation leaves the page waiting for that frame's `load` (no `load` event, no screenshot). So a refused http(s) navigation is let through and stopped as a load: the page itself gets `204 No Content` (the navigation ends and the page stays; the host offers the address in the system browser), a frame gets an empty `403`.
- **Not bridged yet (wolkit gaps).** Wolkit's event records carry a click, hover, keys, focus, the surface's size and the theme for a `surface` node. Pointer motion, separate button presses, wheel deltas, IME preedit and commit for a surface, and an app clipboard are not carried yet; the engine side already takes them (`webengine::input::Input`), so the bridge grows without an ABI change.
- **Ship gate.** Track 2 ships for an app only when the web-app benchmark shows it beating that app's browser window.

## Consequences
- Track 1 ships the mechanism with today's baseline only: until the benchmark posts a number for a row, every profile writes the platform hint and nothing else. Promoting a row is one status change plus the regenerated files (`WOL_REGEN=1 cargo test -p core --lib -- webruntime::`).
- A profile takes effect at the next session start; an app already running keeps its flags.
- Browser policies are machine-wide: tab discard cannot differ per account through the policy file.
- Nothing sets `runtime_discarded` yet; wold passes `false` until a runtime reports its discards.
- The engine's web-platform coverage gaps (media codecs, WebRTC, extensions) decide track 2's migration order; apps the engine cannot run stay on track 1 until it can.
- The runtime, the host window and the policy layer are Rust crates under `crates/`; the manifest format and Store integration are Crystal (Cryswol), per ADR 0036 and 0039.
- The Memory Saver's Settings page becomes the runtime's policy page.
- Wonderland Doctrine: prose says "the Rust browser engine"; dependency identifiers, flag file names and switch names are unchanged.

## Alternatives rejected
- Keep patching each app's bundled engine only: no shared state, chrome stays foreign, cost grows per app. (It stays as track 1 for the apps track 2 cannot run.)
- An embedding of one of the established C++ engines for track 2: mature, but a foreign process model and sandbox, a C++ surface in the system, and no ownership of the policy layer; the lead rejected both.
- Ship the profile switches without numbers: a heap cap below what an app needs crashes its renderer, and an unmeasured flag cannot be defended; hence the `Candidate` marker.
- A new `wol` verb that writes the files at session start: pre-generated files and a small linker keep the session start free of a new interface and make the output reviewable in the image.
