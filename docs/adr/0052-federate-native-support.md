# 0052 - Federate Network addresses, natively
Status: proposed (lead order 2026-11-04 19:25Z, in Portuguese: the browser must support the federate.network protocol natively, with no extension, no opt-in and no opt-out; it just works). Builds on 0042 (the WolOS web runtime), 0048 (system web apps, WWE_1.1) and 0043 (the Atlas browser, draft).

## Context
The Federate Network is "a human alternative web protocol/runtime that runs on top of the existing internet": its own namespace (23 TLDs: `.fed`, `.busca`, `.pagina`, `.pages`, `.cara`, `.comu`, `.oi`, `.weblog`, `.rosa`, `.mosca`, `.tipos`, `.types`, `.foto`, `.pic`, `.vid`, `.sound`, `.records` and six colour names), where every name and every byte is signed and content-addressed. Ordinary browsers reach it through bridges (a DNS server or DNS-over-HTTPS resolver that sends the TLDs to a gateway, or a local daemon on port 80 with a local certificate authority), which the network's own documentation calls convenience mode: the gateway does the checking, the browser trusts it.

What the public material says (read 2026-11-04):
- Landing page https://federate.network/ (`/index.en.md`, `/install.sh`, `/install.ps1`): one DNS setting or the `federate` CLI; `fed://` links; "everything past it is signed, content-addressed, and hash-verified".
- Reference implementation https://github.com/federatenetwork/federate (MIT, Rust, commit e7fc027 of 2026-07-07): `docs/en-US/federate-uri.md` (address grammar), `protocol.md` (root zone, manifests, blocks, HTTP API), `signatures.md` (chain of trust, canonical signing, rollback and expiry), `native-protocol.md` (TCP 4077 framed JSON), `browser-compatibility.md`, `future-federate-browser.md` (a native client "verifies everything itself, trusting no gateway").
- Reference browser https://github.com/federatenetwork/fedsurf (MIT, Tauri, commit dae6055): registers `fed://` as a custom scheme and resolves in process with the reference crates.
- The live network: `https://federate.network/v1/bootstrap` (root key `f7942f5c...e5e6`, `native_nodes` empty), `/v1/root` (root_version 1783402193, 23 TLDs, all root-managed, 3 names), `/v1/domain/home.fed`, `/v1/manifest/41220e29...`, `/v1/block/ddfe588a...`.

The protocol, as implemented here:
- Address: `fed://<label>.<tld>[/path][?query]`; label a-z 0-9 hyphen (1-63, no hyphen at the ends), TLD a-z (2-32); no port, user info or IP; path at most 2048; fragment dropped. `http://home.fed` is the compatibility spelling of `fed://home.fed`.
- Chain: root zone (signed by the root key) -> TLD record (root key) -> domain record (the TLD's operator key) -> manifest (fetched by BLAKE3 address from the domain record, signed by the owner key the record names, for that name) -> content block (BLAKE3 address from the manifest). Path mapping: `/` is the entry, `/x` is `x` or `x/index.html`, `/x/` is `x/index.html`.
- Signatures: Ed25519, hex, over canonical JSON (the record with `signature` set to null, compact, keys sorted at every level). Hashes: BLAKE3, hex.
- A TLD resolves when `official` or `delegated` and not past `expires_at`; a name when `active`, not expired, and `target_type` `manifest`. An unreadable expiry counts as past. A correctly signed older root zone never replaces a newer one.

## Decision
**One verifier, in Rust, shared.** `crates/federate` (BSD-2-Clause, `#![forbid(unsafe_code)]`, no workspace dependency) is the address parser, the canonical encoder, the checks of every layer, a resolver with the root key pinned (`federate::ROOT_KEY`; a new key comes with a WolOS update, never from the network, so there is no trust on first use), the network's HTTPS door as its source (`/v1/root`, `/v1/manifest/<address>`, `/v1/block/<address>` on `https://federate.network`, the system's certificate store, size caps), and the page that says what failed. A source is an untrusted distributor: what it returns counts only after it verifies. The reference implementation's crates are not linked (27 crates with tokio, axum, redb and their own TLS stacks for a daemon; we need the client's checks only); the live network's data is the test vector that keeps the two in agreement.

**The web runtime serves `fed:` itself, always.** The engine library (ADR 0042) registers the `fed` scheme in the engine's protocol table when the engine is made, and the host fills it with WWE_1.2:
```c
typedef void (*wwe_body_fn)(void *sink, const uint8_t *bytes, size_t len);
typedef uint32_t (*wwe_scheme_load_fn)(void *ctx, const uint8_t *url, size_t len, uint32_t kind,
                                       char *mime, size_t mimecap, wwe_body_fn body, void *sink);
typedef intptr_t (*wwe_scheme_map_fn)(void *ctx, const uint8_t *url, size_t len, char *out, size_t cap);
int wwe_engine_set_scheme(wwe_engine *engine, const char *scheme, wwe_scheme_load_fn load,
                          wwe_scheme_map_fn map, void *ctx, char *err, size_t errlen);
```
Each load runs `load` on one of the engine's scheme workers (the engine awaits it; no engine thread waits on the network) and becomes a response with the host's status and content type. At most 8 loads run at once per engine; the rest wait in order, at most 256, and one more is a 503 at once (`src/engine/scheme.rs`), so a page cannot make the process start a thread or a download per subresource. `kind` says whether the load is a document (`WWE_LOAD_NAVIGATION`, a block of at most 64 MiB, the protocol's cap) or something a document loads (`WWE_LOAD_RESOURCE`, at most 16 MiB); verified manifests are held within 8 MiB in all. Before each top-level load of an http(s) URL the library asks `map`; a Federate name under a TLD of the verified zone (or of the network's list before a zone is held) ends that load with `204` and loads the `fed://` address instead, so `http://home.fed` links on the open web open natively too. `webengine::WebView::new` calls `wwe_engine_set_scheme` whenever the library has it: there is no setting, flag or prompt. The pages are a secure context and may `fetch()` their own files (the network's pages load their markdown that way).

**Policy still decides reach.** A web app's policy may name `fed://label.tld` as an origin (every path under it), exactly as it names `https://host`; an app whose policy does not name it cannot open it, as with any other origin.

**Failure is shown, never hidden.** A failed check is a page naming the layer (root zone, TLD record, the name's record, the manifest, the content) and the reason, with status 502, and nothing of the content. A name or path that does not exist is 404, a suspended or expired one 410, a delegated registry or a non-manifest target 501 ("WolOS cannot open this Federate name yet"), an unreachable network 504.

**Atlas.** The browser (ADR 0043, a fork of a large C++ browser) gets the same behaviour through the same crate: a `fed` URL loader factory in the fork's patch series that asks the Atlas bridge (`crates/atlas`, Rust, already planned for AT-9a) to serve each load with `federate::serve`, and the same http(s) mapping for page loads. It is not in this slice: the fork builds only on the forge and the bridge does not exist yet.

**Rollback and time.** No root zone older than the one this build was made with is taken (`verify::MIN_ROOT_VERSION` = 1783402193, the captured zone). The newest zone verified is remembered as version and BLAKE3 digest, in memory and in a sealed file `$XDG_STATE_HOME/wolos/federate/root-version` (read at start; a value below the minimum, or a file that does not open, is ignored; see "Local state" below); an older zone, or another zone of the same version, is refused and the held zone goes on serving. Expiry is judged at the later of the clock and the zone's `generated_at`, so a clock set back cannot bring an expired TLD or name back. Deleting the state file brings the floor back to the built-in minimum, no lower. Signatures are checked with strict Ed25519 (no small-order keys, no malleable signatures). A request path is percent-decoded before it is looked up in the manifest; a malformed escape, a NUL or bytes that are not UTF-8 name no file.

**The http(s) mapping and what it trusts.** An `http(s)://label.tld` page load is taken from the web only when `tld` is in `KNOWN_TLDS` (the 23 TLDs of the zone of 2026-11-04) AND in the held, verified zone's TLD table. On 2026-11-04 none of the 23 is a TLD of the IANA root (checked against https://data.iana.org/TLD/tlds-alpha-by-domain.txt, version 2026110304), so no name of the ordinary web is taken. The zone alone does not widen the list: if the network (or whoever holds its root key) added a TLD that is, or later becomes, an IANA TLD, WolOS would still send those names to the web; a new Federate TLD is reachable as `fed://` at once and through the http spelling after a WolOS update adds it. If ICANN later delegates one of the 23, the update removes it from the list.

**Transport.** The HTTPS door trusts two certificate authorities only, ISRG Root X1 and X2 (`source::ANCHORS`, DER embedded, SHA-256 fingerprints test-checked): the normal Web PKI checks run, but against these roots, so no other authority in the system store, or one a local program adds to it, can stand in for `federate.network`. The server's chain on 2026-11-04 is leaf <- Let's Encrypt YR2 <- Root YR <- ISRG Root X1. The leaf's SPKI (SHA-256, base64 `TSds8bLMkG/y7EyMJFb6AzO9kvuy55yqc94OF/rV9UU=`) is recorded, not pinned: Let's Encrypt leaf keys usually change at every renewal (60 to 90 days) and a leaf pin would turn each renewal into an outage. Rotation path: when Let's Encrypt's next roots (the Y generation, Root YE and Root YR) are trust anchors in their own right, a WolOS update adds them beside X1/X2 before the network's chain stops reaching X1; X1 expires 2035-06-04. TLS carries no trust for content (every byte is signature- and hash-checked); the pin guards what the TLS layer does guard: which server we talk to, privacy of the addresses asked for, and availability.

**Post-quantum status (lead order 2026-11-04 20:19Z).** What a large quantum computer would break, and what WolOS does about it:
- The chain itself (Ed25519 signatures on the root zone, TLD and domain records and manifests) is the network's protocol and is classical: someone able to forge Ed25519 could forge a zone. The specification (signatures.md, future-federate-browser.md, every doc and crate at e7fc027) defines no post-quantum or hybrid signature, so there is nothing to verify yet. `docs/federate/upstream-pq-proposal.md` is our proposal and an issue text for the network (not posted): an optional ML-DSA-65 signature (FIPS 204) beside each Ed25519 one, a root zone that announces it, and clients that then require it. When the network publishes such a field, the verifier checks it when present and requires it when the zone announces it. BLAKE3 content addresses (256-bit) keep a 128-bit margin against Grover's algorithm and stay.
- TLS (done): the server negotiates the hybrid group X25519MLKEM768 (probed 2026-11-04 with OpenSSL 3.6.5). The TLS stack in the tree (rustls 0.23 with the ring provider) has no ML-KEM, so `wolcrypt::tls` (feature `tls`) is a rustls `SupportedKxGroup` for it, built from wolcrypt's X25519 and fips203's ML-KEM-768 (the OS's one ML-KEM; no aws-lc-rs, no new dependency). `source::tls_provider()` puts it first and X25519 after it, and ureq takes the provider through `unversioned_rustls_crypto_provider`, so a server with the group gets the hybrid exchange and one without still answers; the choice is the server's inside an authenticated handshake, so a man in the middle cannot push it down. Tested by an independent-server agreement test and a known answer in `wolcrypt::tls`, and live (`crates/federate/tests/live.rs`, `the_live_handshake_is_post_quantum_hybrid`): offered the hybrid group alone, the handshake with federate.network completes and the negotiated group is X25519MLKEM768 (recorded 2026-11-04). This protects the confidentiality of the addresses asked for against record-now-decrypt-later; content does not depend on TLS. The same group is for the whole OS (`wolcrypt::tls::X25519MlKem768 { rng }`).
- Local state (done): the newest-root-version record (version and digest) is sealed with wolcrypt (`state.rs`): sealed to the hybrid KEM key X25519 + ML-KEM-768 and the sealed bytes signed with the hybrid signature Ed25519 + ML-DSA-65, both derived from a 32-byte key in `state.key` (mode 0600) beside it. A record that does not open is ignored like a missing one. There is no pinned-key file (the key is in the binary) and no disk cache yet.

**Threat note on the local state (honest limits).** The seal stops another user, an edit of the disk while the system is off, and a record copied from another machine. It cannot stop an attacker running as the same user: `state.key` is readable by that user, exactly as it is by the client, so they can read, forge or delete the record. There is no monotonic counter (a TPM NV index would be one; a later task), so putting back an older sealed record of this same machine also works. What such an attacker gains is bounded: deleting or rolling back the state brings the floor back to `MIN_ROOT_VERSION` (the built-in minimum), never below it; writing a higher version makes `fed://` stop resolving until the network catches up (a denial of service, not a forgery: zones are still verified against the pinned root key).

**Engine API note.** At the pin the trait reads `fn load<'a>(&'a self, request: &'a mut Request, done_chan: &mut DoneChannel, context: &FetchContext) -> FutureResponse<'a>` (`FutureResponse` a private alias of `Pin<Box<dyn Future<Output = Response> + Send + 'a>>`); the engine's own example handlers spell it without the lifetime. The shim now spells the trait's signature out; the engine build (ENGINE-build, webengine-wolos on the forge) must confirm it compiles at the pin and fix it there if the engine's main branch has moved (it has: main's signature differs from what was first written here). `Request::is_navigation_request` decides `kind`.

## Consequences
- `fed://` addresses open in every WolOS web view with no install, no extension and no DNS change, and the person's machine checks every signature and hash itself, which the network's bridges do not give an ordinary browser.
- A new dependency: `blake3` (CC0-1.0 OR Apache-2.0, `pure`, no C build). `ed25519-dalek`, `serde_json` and `ureq` were already in the lock.
- The root key is pinned: if the network rotates it (its documentation plans cross-signed rollover), WolOS needs an update. Chosen over trust on first use, which would let the first network answer pick the anchor.
- The HTTPS door is the only source today. When the network lists native nodes, a `Source` speaking the framed protocol on port 4077 slots in without touching the checks.
- Post-quantum: our TLS key exchange (hybrid X25519MLKEM768, `wolcrypt::tls`) and the sealing of local state (wolcrypt) are done. Not yet: the network's own signatures, which are Ed25519 only in its protocol (upstream proposal written in `docs/federate/upstream-pq-proposal.md`, not sent).
- New dependencies in the tree: `crates/wolcrypt` and its pure-Rust crates (fips203/204/205, curve25519-dalek, zeroize, chacha20poly1305, pbkdf2), copied byte-identical from `wave3/trust-core` bac02b70 apart from the `tls` module and feature; `rustls` (already in the lock through ureq) as an optional dependency of wolcrypt.
- Not yet: delegated TLD registries (`delegated_manifest`, `delegated_native`, `delegated_http`; none exists in the live zone), a disk cache of verified zones and manifests (offline use), http(s) subresources of Federate names (only page loads are mapped), a start URL spelled `http://name.tld` (the host gate sees it before the library maps it), mapping a frame's navigation, and Atlas. The shim's half compiled at the pin without changes and ran in the real engine on the forge guest (ENGINE-FED, 2026-11-05); the one fix it needed is the mapped load's retry (docs/modules/webengine.md).
