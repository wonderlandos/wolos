# ADR 0043: Atlas, the WolOS browser: a patch series on an org fork, Rust side components over a stable boundary

Status: proposed (lead order 2026-11-03). Decisions D1 to D9 are the architect's proposal; the open calls are listed at the end under "Decisions needed from the lead". D4 describes the bridge as built.
Wonderland Doctrine: this text never names the upstream fork, its authors, the engine's vendor or another browser; attribution lives in `docs/THIRD-PARTY.md` and the licence files shipped in the package. Where this text says "the fork" it means our org fork of the browser WolOS repackages today; "the engine" is the open-source browser engine it builds on.

## Context

- Today WolOS repackages the upstream x86_64 release tarball (the browser package in `wolos-pkgbuilds`: signature checked, installed under `/opt`, our launcher, desktop file, policy file and first-run prefs from `wolos-system`). We own no engine behaviour: the name, icon, About page, services, update and crash endpoints, and every default are the fork's. The user data dir, URL scheme and process names carry the fork's brand.
- Measured on the release of 2026-10-30: tarball 123 MB xz, 410 MB unpacked: main binary 296 MB (stripped), 221 locale packs 52 MB (the 12 WolOS languages need 9.3 MB), chromedriver 22 MB (the browser does not need it), `resources.pak` 19 MB, ICU data 10.8 MB, software Vulkan 4 MB. The binary still carries the strings of features the fork disables (assistant hooks, Lens, autofill, media router, optimization guide): a build flag, not a patch, removes the code.
- The fork is itself a patch series: 346 patches (about 91,000 patch lines; 256 files are the fork's own, the rest inherited from privacy-patch projects), applied with `utils/patches.py` onto a prepared engine source tarball, then domain substitution, a name substitution pass (the engine's product names to the fork's name in `.grd`/`.xtb`), i18n, resources, `gn gen`, siso/ninja. Platform glue is a second small repo (6 Linux patches, `flags.linux.gn`, build scripts), which already accepts extra patch directories. It releases about twice a week (14 releases between 2026-09-08 and 2026-10-30), following the engine's stable channel (156.0.8078.47 today, merged 2026-10-21).
- Facts from the fork that matter to us: Memory Saver is already enabled by default and "infinite tab freezing" is on; Global Privacy Control exists as a pref but defaults off; Do Not Track defaults off; "services" (update checks, crash upload, bangs, extension download proxy, filter-list assets) default on after an onboarding consent and talk to the fork's own hosts; policies are read from `/etc/chromium/policies/managed`; component updates are re-enabled; the Linux platform patch forces the GTK system theme (what WolOS wants).
- WolOS already has the pieces a first-class browser should use: libwol 1.15 on `wave3/cr12` (`wol_file_trash`, `wol_share_file`, `wol_open_with`), the helper gate and approval sheets (`wol mcp`, ADR 0020), the Memory Saver (ADR 0026: the browser with 20 tabs, four apps 3618 to 1450 MiB PSS, but background tabs fault back to about 2400 MiB after 4 minutes), xguard's first-use check on downloads (ADR 0024/0028; it keys on the `user.xdg.origin.url` attribute browsers write), a login keyring unlocked at login, the QoS service (nice/ioprio classes now, scx_wolos not shipped in 0.12), and the web-app runtime on the Rust engine (ADR 0042, `wave3/wa2e`).
- The lead wants the browser to be to WolOS what the platform browsers are to the two big desktop platforms: first-class, branded Atlas, integrated, lean, fast, private, and still receiving upstream updates cheaply.

Provenance of this draft: kernel fork model, ADR 0026, ADR 0042, the helper gate and the Memory Saver numbers come from memory/repo and were re-checked against the files named above; the fork layout, release cadence, size breakdown and CI timings are fresh measurements of 2026-11-03 (a read-only shallow clone under `.claude/tmp/atlas`, the release asset listing); build-time and saving figures marked "estimate" are not measured yet and AT-1/AT-4 replace them.

## Options considered

1. Keep repackaging the upstream binary, rename in the launcher and desktop file only. Cheapest; rejected as the end state: the About page, URL scheme, data dir, services, defaults and size stay foreign and every wish in this ADR is impossible. It stays as the fallback until the Atlas lane is green (gate G2).
2. Patch series on our org fork, built by us, plus Rust side components (chosen).
3. The engine's content layer with a Wolkit-drawn chrome (tabs, omnibox, menus in Rust/Kit). Truest to "native", but it is a browser rewrite: tab strip, omnibox, extensions UI, devtools, downloads, printing, permissions, accessibility. Years, not weeks, and every engine release breaks it. Rejected.
4. Another engine (another engine, or the Rust engine of ADR 0042) as the main browser. Site compatibility, DRM, WebRTC, extensions and devtools gaps; the lead already rejected embedding a browser engine in the web-app runtime for process-model reasons, and Atlas must stay the full browser. Rejected for Atlas; ADR 0042 stays the answer for installed apps.
5. Take an existing privacy-patch project (without the fork) as the base. Fewer features and no UI work done; we would redo what the fork already carries (importers, layouts, vertical tabs, filter-list component, onboarding). Rejected: the fork is the better base and the overlay model makes a later base change a one-directory job.

Premortem of the favourite (option 2), written as if it failed in six months: (a) an engine security release arrives and our lane needs two days to rebase and build, so users run a vulnerable browser (mitigation: warm cache lane, overlay patch budget, a security-release runbook with a 24 h target, see Update cadence); (b) our patches rot faster than we fix them because we edited inherited patches (mitigation: never edit inherited patch files, overlay only, transform scripts over patches for renames); (c) the 128-core forge is busy with the test battery and the nightly never runs (mitigation: a lock, a night slot, S3 cache so any box can resume); (d) the rebrand strands users' cookies and sessions (mitigation: keep the keyring lookup identifiers unchanged, migrate the profile directory, e2e journey); (e) licence confusion between the fork's GPL-3.0 and our GPL-2.0-or-later code (mitigation: separate processes and a written rule, below); (f) the product name collides with another product of the same name (see Risks). Nothing in (a) to (f) argues for option 1 or 3; they argue for keeping the patch budget small and the lane fast.

## Decision

D1. Atlas is our build of the engine plus the fork's patch set plus an Atlas overlay. Name: Atlas; package `atlas-browser`; binary `/usr/bin/atlas` (launcher) and `/opt/atlas/atlas`; app id and desktop file `atlas`; user data `~/.config/atlas`; URL scheme `atlas://`; policy directory `/etc/atlas/policies/managed`; first-run prefs `/usr/share/atlas/initial_preferences`.

D2. Repository model (the kernel fork model, adapted). The kernel fork is "upstream plus one commit per patch" because the kernel tree is the repo. The browser source (tens of GB) cannot be the repo, so the repo is the patch repository:
- Branch `upstream`: fast-forward mirror of the fork's main. We never commit to it.
- Branch `atlas` = `upstream` + the directory `atlas/` only: `atlas/patches/series` and `atlas/patches/<area>/NNNN-name.patch` (one commit per patch file, commit message = patch header), `atlas/flags.atlas.gn` (appended after the inherited GN args, so ours win), `atlas/transform/*.py` (scripted substitutions with asserted match counts), `atlas/resources/` (the brand slot), `atlas/platform/` (the Linux glue: the 6 platform patches renamed, build script, `docker/` build environment), `atlas/tests/` (gate manifests). The inherited patch files and series are never edited, so `git merge upstream` is conflict free by construction; conflicts appear only when the overlay is applied to a new tree, and they are fixed in our patch, never theirs.
- The effective series is: inherited series, minus `atlas/drop.list` (a leaf-only list; the tool refuses to drop a patch that a later one depends on, by dry-run apply), plus the overlay series. `utils/patches.py` already accepts several patch directories; `atlas/tools/atlas-series` builds the combined view.
- Tags `atlas-<chromium version>-<n>` pin a release; the PKGBUILD pins the tag, the source tarball hash and the toolchain revisions. Unshipped experiments live as `archive/<name>` tags, as for the kernel.
- The repository is renamed from the fork's name to `wonderlandos/atlas` (lead call; GitHub keeps the fork link, which is the licence-correct provenance). Branch protection and the release key follow the kernel fork.

D3. Patch budget and the "transform over patch" rule. Every patch is a recurring cost. Order of preference for any change: (1) a GN argument; (2) a policy or a first-run preference; (3) a launcher flag or `Feature` override on the command line; (4) a scripted transform with asserted counts (renames, string substitutions: robust to context shifts); (5) a patch of one to a few lines; (6) a new component. Budget: at most 60 overlay patches and 2,500 added C++ lines by 0.14; each patch has a header (why, files, test filter, rebase risk) and a test in the gate manifest. A patch that fails to apply for two milestones in a row is a candidate for deletion, not heroics.

D4. Rust side components over a stable boundary. No Rust is compiled into the engine: the engine's in-tree Rust needs vendored crates and the engine's own toolchain pin, and it would make our code a derivative of the fork's licence. Instead:
- `atlas-bridge` (crate `crates/atlas`, GPL-2.0-or-later; it depends on `shared` only): a systemd user service, socket-activated at `$XDG_RUNTIME_DIR/atlas/bridge.sock` (0600, in a 0700 directory) by `atlas-bridge.socket`, installed as `/usr/lib/atlas-bridge`; it exits after 30 s with no connection and nothing waiting for the person, and holds a few MB while the browser keeps a connection. It is the only code in the Atlas stack that asks wold for anything. It does so as built: it speaks wold's portal wire through `shared::portal` and `shared::jobs` (the calls `share.file`, `open.with`, `file.trash` that libwol 1.15 sends), so it needs no libwol link, no new dependency and no edge in the crate graph (`crates/shared/tests/architecture.rs` is unchanged). On a WolOS without libwol 1.15 wold answers "not a known call": Share and Trash then say `unavailable` and Open With falls back to `xdg-open`. wold names a program by its executable, so the grants `share` and `trash` in `/etc/wolos/consent.json` are for `/usr/lib/atlas-bridge`, a small checked program, and not for the browser. The one `unsafe` block is `UnixListener::from_raw_fd(3)` for socket activation (`LISTEN_PID` checked), counted in the ratchet in `crates/shared/tests/unsafe_ratchet.rs`. It verifies the browser's identity by `SO_PEERCRED` plus the pinned `/proc/<pid>/exe` check used for MCP helpers (audit C10-6), so only `/opt/atlas/atlas` is "the browser".
- `atlas_host` (C++ component in the overlay, about 800 to 1,200 lines at 0.13, BSD-3-Clause like the engine): a thin client of the bridge protocol inside the browser process. It owns about eight hook sites (download completion, context-menu items, tab/process lifecycle, memory pressure injection, install-as-app, helper requests). It does no WolOS logic.
- The boundary is a versioned wire protocol ("Atlas Host Protocol", version 1, line-delimited JSON, like `shared::shell`), specified in `docs/modules/atlas.md`; its types are `crates/shared/src/atlas.rs` and its fixtures `crates/shared/tests/fixtures/atlas/`, shared byte for byte with the browser component's test data, with tests on both sides and a fuzz target (`atlas_wire`). A change to either side that keeps the version is safe; engine upgrades touch only `atlas_host`'s hook sites.
- Generated settings: the policy file, first-run preferences and launcher flags become typed Rust (`crates/core/src/browser.rs`, successor of the current browser theme module in `crates/core/src/theme`), tested against the engine's policy list in the lane (every key must exist in the tree's policy definitions).

D5. Integration surface (each item is a work package in `plan-atlas.md`):
- Share, Open With, Move to Trash: context-menu and download-bubble items call libwol 1.15 verbs through the bridge. 0.13.
- Sealed downloads: a finished download is checked by xguard (its scan API) before Atlas offers Open; the verdict is shown in the download bubble with WolOS wording; fail closed (ADR 0024 "unchecked" refuses). The attribute browsers already write is what the guard keys on, so a browser without the hook is still protected; the hook adds the visible state. 0.14.
- Keyring: the login keyring is unlocked by `wol-login`; the session desktop name is not one the engine recognises, so the engine may fall back to its plaintext "basic" store. Atlas selects the libsecret backend explicitly (launcher flag now, default patch later) and the gate checks the cookie database prefix (`v11`, not `v10`). 0.13.
- Memory Saver: Atlas keeps the browser's own tab freezing and discarding (already on) and tunes it to ADR 0026's numbers; the OS Memory Saver keeps paging out the rest of the process tree. A pressure feed from wold to the engine's memory-pressure listener makes both decide on the same signal. 0.13 defaults, 0.14 feed.
- Tab QoS: renderer processes get a class from visibility and audio state (foreground tab, visible window, hidden tab, playing media) through the bridge to the QoS service (nice and ioprio classes on a stock kernel; scx_wolos classes later). Needs one new portal call and libwol symbol for "hint a pid in my own app scope" (API owner; ABI rule: added in a new node). 0.14.
- AI helpers: Atlas ships no assistant of its own. It exposes a small `wol browser` verb family to helpers (tabs list, page text, open URL) through the existing gate: every call is an approval sheet unless the person allowed that helper and capability; private windows are never exposed; the audit line names the tab origin only. 0.14.
- Installed web apps: ADR 0042's runtime owns installed apps. Atlas stays the full browser (tabs, extensions, DRM, WebRTC, devtools). "Install as app" in Atlas calls `wol webapp add` (Change capability, asked every time, per C10-1). Until the runtime covers a site, the launcher keeps `--app=` windows working on a lean app profile. Boundary: no shared profile, no shared site data.
- Native feel: the engine follows the WolOS GTK theme and the settings portal (light/dark today); Atlas adds the portal accent as the engine's theme seed (0.14), WolOS tokens for Atlas WebUI pages, HIG sizes where the engine's layout system allows (toolbar 36, radius 6/10), and the compositor's strip for window buttons (already). A brand slot (`atlas/resources/brand`, file list in `patches-0.md`) receives logo, icon, new-tab and first-run showcase from the brand package.

D6. De-bloat is a package, not a rewrite. Every engine feature, service and bundled component WolOS never ships is removed behind a GN argument, a transform or a policy, listed in `atlas/debloat.toml` (name, mechanism, expected saving, measured saving, owner test). The list is measured, not assumed: AT-4 attributes the existing binary by source directory with a size profiler, then ships only flags with a measured gain and a green gate. Package-level trims need no engine change and ship first: 12 locales (about 43 MB), chromedriver out of the runtime package (22 MB), debug symbols kept as a separate nightly artifact. Honest expectation: de-bloat buys disk, attack surface and some startup; page memory comes from the process model and tab policy, not from removed features.

D7. Build lane. The heavy compile is a lane, not a chroot package: the engine build needs 100+ GB, network for toolchains and a day on a small box. The lane runs on the 128-vCPU forge (nightly and on demand), produces a signed tarball (the same layout as today's upstream release, plus a symbols zip and a manifest of source tag, tarball hash and toolchain revisions), and `wolos-pkgbuilds/atlas-browser` repackages that artifact exactly as the current browser package does today (source URL, sha256, `validpgpkeys` = our release key). Packaging therefore stays the one clean-chroot path of ADR 0029; only the compile is the exception, recorded here.

D8. Not done in the engine (hard line): no changes to the engine's renderer, JS runtime, graphics library, network stack, the sandbox design, the codec stack or the renderer process architecture beyond flags, defaults and kill switches; no own sync service in 0.13/0.14; no own extension store; no own updater (pacman/wopkg only); no own crash server (crash dumps stay local); no ad or search deals; no AI features of our own in the browser; no replacement of the views UI toolkit by Wolkit; no JS engine swap; no bundled DRM module (the DRM module is an optional package, never default).

D9. "bun optimisation": nothing in the engine or the fork carries that name. We read the order as JS runtime and page-memory tuning (the JS runtime's flags, renderer and process model, tab discarding tied to the Memory Saver), accepted only on bench numbers. If the lead meant a third-party JavaScript runtime in the build (replacing the pinned one used for WebUI resources), we advise against it: unsupported upstream, a few minutes of a 1 to 2 hour build, and a hermetic toolchain we then own. Flagged for confirmation.

## Update cadence

- Source of truth for engine version: the fork's releases (about 2 per week; each tracks an engine stable or security point release).
- Monday merge window (weekly): merge `upstream`, run `atlas-series --dry-run` on the new prepared tree, rebase failing overlay patches, build, gate. An engine major (about every 4 weeks) gets two days budgeted; a point release is expected to take hours.
- Nightly: apply, build (warm cache), bench, gate on the head of `atlas`. Red nightly blocks the next release, not development.
- Security runbook: when an engine release is marked exploited in the wild, target 24 h from the fork's release to our signed artifact (warm-cache incremental build is about 35 to 60 minutes, estimate; upstream's own cached x86_64 build took 27 minutes on 2026-10-30). If our lane is red, we fix the lane first, and we do not ship an unpatched engine: the old artifact stays and the lead is told.
- Users get Atlas through the normal `wopkg` channels (stable follows the WolOS release; a security channel for Atlas security bumps is proposed, lead call).
- We do not send patches upstream; we carry them. Nothing in the overlay depends on upstream accepting it.

## Build lane (summary; details in plan-atlas.md)

Forge: 128 vCPU, 256 GiB, instance-store NVMe (wiped when the box stops), so the lane keeps sources and `out/` on `/scratch` and the compile cache in S3 (sccache with the S3 backend; the inherited build script already wires `cc_wrapper` to sccache or ccache, and the siso remote-execution path). Static official build for the nightly and the release; component build (`is_component_build=true`, symbol level 0) only for patch authors, with incremental links in seconds. No PGO in 0.13; PGO phase 2 (profiles are binary data fetched at build time) evaluated in 0.14 on bench numbers. Toolchains (clang, Rust, Node, sysroot) are fetched from the engine's storage at build time: the lane mirrors them to our S3 bucket for reproducibility and records their hashes in the manifest. Lock file so the test battery and the Atlas lane do not run together; no AWS quota request (share the existing boxes).

## Licence notes

- The engine is BSD-3-Clause with many third-party licences (some LGPL/MPL); the fork's own patches and tooling are GPL-3.0; inherited patch sets carry their own licences (BSD/MIT/GPL). The Atlas binary as distributed is therefore a combined work distributed under GPL-3.0-or-later with the engine's notices; the package `license=` lists `GPL-3.0-or-later AND BSD-3-Clause` plus the third-party set, and installs `/usr/share/licenses/atlas-browser/` with the fork's LICENSE, the inherited-patch licence file and a generated third-party list (the engine's credits page is built from the same data).
- Our overlay patches that modify fork files are `GPL-3.0-or-later` (the fork's licence). New files we add inside the engine tree (`atlas_host`) are `BSD-3-Clause`, same as the engine, so they can move to any tree built on the same engine.
- WolOS code stays what it is: `atlas-bridge` and `crates/core/src/browser.rs` are `GPL-2.0-or-later`, libwol and the C SDK are BSD-2-Clause. "GPL-2.0-or-later" can be combined into a GPL-3.0 work by choosing version 3, but we do not rely on that: the bridge is a separate program talking a documented protocol (aggregation, not linking), so the licences never mix in one binary. Rule: no WolOS GPL-2.0-or-later source file is compiled into the browser; no engine or fork source file is linked into a WolOS program. The `atlas_host` component is original BSD code with no WolOS source in it.
- Attribution: only in `docs/THIRD-PARTY.md` (a new section "Atlas browser engine" naming the fork, the inherited patch projects and the engine, with licence texts exactly as shipped) and in the package's licence directory. Never in code comments, UI strings, docs prose, package descriptions, the About page body or the site. The About page shows Atlas, the WolOS release and the engine version; the engine credits page (required by the engine's licences) is kept.
- Trademarks: the engine's and the fork's names and logos are not ours; the build removes the fork's brand assets and uses only the brand package. Codec patents: the inherited build enables proprietary codecs (H.264/AAC via the engine's media library); WolOS already ships that in the repackaged binary; the lead should confirm the policy for the project (no change proposed here).
- This is engineering guidance, not legal advice; a licence review before the first Atlas release is on the plan.

## Risks

1. Patch rot and security latency (premortem a, b): mitigated by the budget, overlay-only rule and nightly lane. Residual: high; an engine major can break 10 to 20% of overlay patches (estimate).
2. First build never goes green (toolchain downloads, disk, memory): gate G1 on day 4 of the plan; fallback is to stay on the repackaged binary for 0.13 and ship only what needs no engine (policies, launcher, package trims). The rename must not ship half way (an Atlas icon over a foreign About page breaks the Doctrine): lead call at G2.
3. Supply chain of the prepared source tarball: it is produced by the fork's maintainers from the engine's git; we verify its published hashes now, mirror it to S3, and plan our own preparation script (from the engine's tag) in 0.15 so one party is not a single point of trust.
4. Forge contention and instance-store wipes (memory: idle stop, metal boot about 10 min): lock, S3 cache, build resumes from cache.
5. GPU acceptance cannot be fully tested on the forge or in a software-rendered VM (no GPU, and the AWS GPU quota may not allow one without a raise, which is not allowed): hardware acceptance is manual on the lead's machines; automated checks cover flags and the GPU info page only.
6. Profile and keyring migration: the rename must keep the engine's keyring lookup unchanged and move the profile directory once; journey J-A9 is a release blocker.
7. Name collision: the name Atlas is in use for other products, so trademark and search confusion are possible (not legally reviewed). Mitigation inside our control: always "Atlas for WolOS", package `atlas-browser`, app id `atlas`. The final call is the lead's.
8. Services that phone home: the inherited default is "on after consent" to the fork's hosts. Atlas disables the services feature, empties the update and crash hosts and blocks the extension-download proxy; the gate runs a zero-egress test (idle 30 minutes, DNS and socket log, nothing but the test corpus).
9. Effort is large: 0.13 is about 224 focused hours plus 60 to 80 forge hours (plan-atlas.md). If two workers are available, the critical path is the baseline build and the rename; everything else parallelises.

## Consequences

- WolOS owns the browser's name, defaults, size and integration; the price is a build lane to keep green and a weekly merge duty.
- The current browser package is replaced by `atlas-browser` (package `Replaces`/`Conflicts`); WolOS code that names the old browser (theme module, web-app launcher, shell window rules, Dock pins, mime defaults, icon aliases, lint script) changes in one commit set (AT-6).
- Installed-app work (ADR 0042) and browser work share only the bench vocabulary and the Memory Saver policy language.
- New wire contract (Atlas Host Protocol) and new capability names for helpers (`browser`), documented in `docs/modules/atlas.md` and `docs/modules/automation.md`.
