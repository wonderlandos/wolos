# 0061 - Runtime tuning: kernel and userland memory for JavaScript engines
Status: accepted (lead order 2026-11-04: Bun, WebKit and V8 faster, less GC, less memory, Discord at 100 MB without a new Discord, at kernel and userland level; measured in VMs on the 0.12.1 install, numbers in [bench/js-runtime-x.md](../bench/js-runtime-x.md)). Builds on 0026 (Memory Saver) and its 0027 amendment (per-app budgets), which decide *when* an app is held; this record decides *what the engines and the kernel are given*.

## Context
Third-party apps bring their own engine: Electron and Chromium (V8, PartitionAlloc), WebKitGTK (JavaScriptCore, bmalloc), Bun (JavaScriptCore, mimalloc). Their memory is not the engine's heap alone. On the Discord login page (Electron 44.10, Chromium 152) 534 MiB of PSS split as: PartitionAlloc 142, the V8 heap 61 (+29 for V8 code and tables), the 218 MB binary's code 103 and read-only data 76, shared memory 14, native modules 25. 40 % of it is file-backed. Engine flags moved none of it: 16 flag and environment rows measured, 2 helped.

## Decision
1. **Fault-around 4096** (`/sys/kernel/debug/fault_around_bytes`, default 65536). A page fault on a mapped file maps the 16 pages around it; every mapped page is in the PSS of every process that maps it, used or not. At 4096, file-backed PSS of Discord goes 215 -> 126 MiB (curve: 164 at 16384, 144 at 8192). Cost: about 8 % more CPU and 45 % more minor faults during the start, window and frame times unchanged (6 runs each).
2. **KSM for the engines' process trees, on a machine with one human account only.** `wolos-mm exec-merge -- /abs/path/app` sets `PR_SET_MEMORY_MERGE` before the exec (inherited by every child, exec included; a bare command name is refused, the path is what runs); 500 pages every 100 ms. ksmd sleeps while no process asked, so nothing runs without such an app; with one it takes about 2.5 % of a core in the first minutes and falls. WebKitGTK: anon 577 -> 459 MiB; Electron: -22..-26 MiB of anon in 8 of 8 paired runs. **The side channel, plainly:** KSM merges identical pages of every process that opted in, across processes and across users, and a write to a merged page (copy-on-write) is measurably slower than to a private one. A process of one person can therefore learn whether another person's process holds a page with a given content. It stays off wherever there is another person: `wolos-mm apply` (boot, `wolos-mm.service`) writes `run=1` only when the passwd file has exactly one human account (uid 1000 and up with a login shell, the list Settings > Accounts and the Setup Assistant keep: `settings::users::parse`), otherwise `run=0` and a journal line says how many accounts it counted; `exec-merge` applies the same rule and then asks the kernel for nothing. A machine that gains a second account turns it off at the next boot (`wol_core::jsruntime::ksm_policy`; both branches are tested with a fake passwd file).
3. **Bun**: `MIMALLOC_ARENA_EAGER_COMMIT=0` and `MIMALLOC_PURGE_DELAY=0` for every Bun we start: peak RSS of the site build 888 -> 321 MiB at the same wall time.
4. **Page-out** of an idle app is `wolos-mm pageout [--any] PID [anon|all]` (`process_madvise(MADV_PAGEOUT)`, one call per range). It does not depend on which cgroup the pages are charged to (a `memory.reclaim` of the scope moved 34 MiB where this moved 215), so an app that was not born in its scope is reachable. **One filter, two callers:** `wol_core::jsruntime::pageout_ranges` says which mappings are asked about (default: writable anonymous memory, memfd and /dev/shm, writable file data; `all` adds read-only data and the code); `wolos-mm pageout` and Memory Saver (`crates/api/src/memsaver/pageout.rs`, which decides when) both call it, and its single test table is in `jsruntime.rs`. **Who may be paged out:** the tool opens a pidfd first and reads the cgroup, the owner and the maps only after, and checks the pidfd still names the process before the first call; it refuses a target that is not the caller's own user's or not inside an `app-*.scope` (exit 3), and `--any` lifts that for root only. With 1-3 in place and the page-out every 30 s while the window is behind, Discord is at **96-104 MiB of PSS** in the background (10 minutes), 115-128 MiB twenty seconds after it is brought back to the front, and answers a script call in 2-6 ms.
5. **Lean mode** (apps held to a budget): V8 `--lite-mode` (-13 MiB), JSC `useJIT=false` (WebKitGTK -92 MiB, Bun -82 MiB) cost script speed by a large factor. They are rows with their numbers, applied only when the caller asks for `Mode::Lean`; nothing uses them by default.
6. **One source for the tables**: `wol_core::jsruntime` (`ROWS`, `MM_WRITES`, `ksm_policy`, `runtime_flags`, `pageout_ranges`, `pageout_allowed`). The boot knobs are written by one oneshot, `wolos-mm.service` (`wolos-mm apply`, after `sys-kernel-debug.mount`), not by a tmpfiles file, because the KSM switch depends on the accounts. A row that measured no gain stays in the table as `NoGain` with its number.

## Not decided here
- When to page out, and the budget numbers: Memory Saver (0027). The launch path calls `runtime_flags(class, mode)` and puts `Runtime::prefix()` in front of the app.
- The kernel carries `fault_around_bytes` only in debugfs; under `lockdown=integrity` it cannot be written. The kernel lane takes a `vm.fault_around_bytes` sysctl (docs/modules/runtime-tuning.md, "Kernel lane").

## Consequences
- `wolos-mm` is a new program (`crates/controller/src/bin/wolos-mm.rs`) with two `unsafe` blocks (`unsafe_ratchet` controller 56 -> 58, `rules_rust` RR-068 55 -> 57) and a new unit, `wolos-mm.service`. `wolos-mm ksm` is a status dump printed once, not a governor: there is no loop.
- Machine memory (MemAvailable) does not change with fault-around: those pages stay in the page cache. The gain is in what each app is *charged* and in what a page-out of the app can free. The record says which number is which.
- 100 MiB is reached on the login page, in the background, with the page-out running. In front, with the page-out not running, the floor of these measures is 457-470 MiB (fault-around and KSM) on Discord; a logged-in client holds more of its own heap than the login page (not measured: no account).
