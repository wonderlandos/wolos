### Standards (state at 2026-11-04; [fresh] from knowledge, not fetched by this worker)
- FIPS 203 ML-KEM, FIPS 204 ML-DSA, FIPS 205 SLH-DSA: final since August 2024. NIST IR 8547: classical public-key algorithms deprecated after 2030, disallowed after 2035. HQC is the second KEM NIST picked (2025), not yet a FIPS.
- Hybrid key establishment is the deployed practice: X25519MLKEM768 in TLS 1.3 (draft-ietf-tls-ecdhe-mlkem, on by default in Chrome, Firefox and Cloudflare), `mlkem768x25519-sha256` the default of OpenSSH 10, X-Wing (draft-connolly-cfrg-xwing-kem) the same pair as a generic KEM. A reader must break both halves.
- Symmetric crypto needs no new algorithm: Grover halves the key length, so 256-bit keys (AES-256, ChaCha20) keep 128-bit security. Argon2id (RFC 9106) is the memory-hard password KDF; NIST SP 800-132 approves PBKDF2 only.
- Rust implementations: WolOS already ships, in `crates/wolcrypt` (ADR 0046, Fable audits 1 and 2), fips203 / fips204 / fips205 =0.5.0 (integritychain, MIT OR Apache-2.0, pure Rust, no independent audit known; cross-checked in-tree against RustCrypto `ml-dsa` and the NIST ACVP vectors), curve25519-dalek 4 (BSD-3; an older audit exists, not re-checked here), chacha20poly1305 0.10.1 (RustCrypto, MIT OR Apache-2.0, NCC Group audit 2020), pbkdf2 0.12. Alternatives considered: RustCrypto `ml-kem` 0.3 / `ml-dsa` 0.1 (pre-1.0, no audit known), aws-lc-rs (Apache-2.0 / ISC, AWS-LC has a FIPS 140-3 validation with ML-KEM, but a C and assembly build with cmake, which wolcrypt was made to avoid: lead decision "WOLCRYPT, no ring"), libcrux-ml-kem (Cryspen, Apache-2.0, formally verified, the code OpenSSH took; a good second implementation for a cross-check later), liboqs via `oqs` (MIT, C, the project calls itself research-grade).

## Decision

### 1. One crypto crate for the whole OS
Every WolOS-owned format does its cryptography through `crates/wolcrypt`: hybrid signatures (Ed25519 + ML-DSA-65), the hybrid KEM (X25519 + ML-KEM-768 with a key schedule bound to both ciphertexts, both public keys and the header), ChaCha20-Poly1305, SHA-512, PBKDF2. A format whose signature or KEM is fixed by an outside specification (federate: Ed25519 + BLAKE3, ADR 0052) keeps that algorithm and says so in its ADR. There is no classical-only entry point in wolcrypt and none in the keyring.

The keyring lives in a new crate `crates/wolkeyring` (BSD-2-Clause, no `unsafe`): the pure core (formats, policy, access control, audit chain, bundle, move protocol), a small I/O layer (files, randomness, `systemd-creds`, `fprintd`, `fido2-assert`), the daemon `wol-keyringd` and the command `wol-keyring` (`wol keyring` in the command tree).

### 2. The store (`wolos/keyring/1`)
- [fresh] One file per keyring, `~/.local/share/wolos/keyring/<name>.wkr`, mode 0600, never through a symlink. A header (JSON, length-prefixed) and then an append-only list of records. A write appends one record and calls `fsync`; compaction rewrites the file atomically (temp file, `fsync`, rename, `fsync` of the folder).
- Keys: a random 32-byte **master key** MK. MK seals a key block: `dek_wu` (secrets of items that are readable only while the keyring is unlocked), `dek_afu` (secrets readable after the first unlock until the session ends, and the metadata of every item), and `id_seed` (the keyring's own hybrid identity: an X25519 + ML-KEM-768 recipient key and an Ed25519 + ML-DSA-65 signing key, `wolcrypt::kem::EncSecret::from_seed`, `wolcrypt::sign::SigningKey::from_seed`, each from its own derived seed).
- Every AEAD key is used once: a record's key is `SHA-512(len-prefixed "wolos/keyring/1/rec", store id, record number, a fresh 32-byte salt, the class key)`; key = bytes 0..32, nonce = 32..44. Associated data is the record header (format, store id, record number, salt, the previous record's chain value), so a record moved, replayed into another store, reordered or dropped from the middle does not open.
- Symmetric cipher: ChaCha20-Poly1305 (wolcrypt), not AES-256-GCM: the same 128-bit post-quantum margin, constant time without AES-NI, already audited and in the tree; AES-256-GCM would add four crates for no security gain (question Q2 in #plan 9151).
- Items: `id` (16 random bytes), collection, label, attributes (string map, as the Secret Service has them), the secret (bytes and content type), created/modified, class (`when-unlocked` default, `after-first-unlock` for things a background service needs while the screen is locked, such as the VPN key), `this-device-only` (never exported, like Apple's ThisDeviceOnly), and the access list (section 4). The metadata is encrypted too (gnome-keyring keeps attributes in clear): nobody learns which sites a person has passwords for from the file.
- Limits: at most 65 536 items, 64 KiB per secret, 8 KiB of metadata per item, 64 MiB per file; a reader refuses more before it allocates.

### 3. Unlock factors and policy ("from fingerprint to everything")
Each factor gives a 32-byte factor secret; a **rule** is a set of factors that together unlock; the policy is a list of rules, any one of which unlocks (so "n of m" is the rules that are the n-subsets). For each rule the header keeps one wrap of MK: `key = SHA-512(len-prefixed "wolos/keyring/1/wrap", store id, rule id, a fresh 32-byte salt, then each factor id and factor secret in factor order)`. There is no secret sharing arithmetic to get wrong; a policy of 6 factors with any 3 is 20 wraps.

| Factor | Factor secret | Notes |
|---|---|---|
| `password` | KDF(login password, salt) | Argon2id m=64 MiB t=3 p=1 (RFC 9106, RustCrypto `argon2` =0.5.3, approved by the CTO in #plan 9168; checked against the RFC 9106 section 5.3 vector in `tests/kat.rs`); PBKDF2-HMAC-SHA512 600 000 (wolcrypt) is still read and may be chosen where an SP 800-132 KDF is required. The header names the KDF and its parameters; a reader refuses parameters below the floor (Argon2id 19 MiB x 2 passes, PBKDF2 210 000 rounds: no downgrade) and above the ceiling (1 GiB, 10 passes, 8 lanes, 10 000 000 rounds: a hostile file cannot cost unbounded time) |
| `pin` | KDF(PIN, salt) | Only in a rule together with `tpm` (a PIN alone is brute-forced offline in minutes); the TPM's dictionary-attack lockout limits online tries |
| `tpm` | 32 random bytes sealed by `systemd-creds --user encrypt --with-key=tpm2 --tpm2-pcrs=7` | The device key: unlocks at login on this machine only. Refused on a machine without a TPM2 (it would be a key next to the lock). What it is sealed to [fresh, from `man systemd-creds` 255]: the TPM's storage key and **PCR 7 only** (the Secure Boot state and its certificates), no other PCR, no TPM authorisation value or PIN. `io::tpm_seal` names `--tpm2-pcrs=7` explicitly so a change of systemd's default cannot silently change it. Consequences: (a) a copy of the disk without this TPM cannot open the factor; (b) any code that runs on this machine under the same Secure Boot state can ask the TPM to unseal it (another OS signed by a key in `db`, a kernel or initrd of the same chain, any process of the same user through `systemd-creds`), so the factor is *convenience at sign-in*, not a barrier against local attackers; the PIN factor does not change that because the PIN is stretched on the host, not checked by the TPM; (c) a change of the Secure Boot keys or a firmware reset changes PCR 7 and the factor stops working until the password or recovery code re-enrols it; kernel, initrd and bootloader updates do not break it. A policy bound to the signed PCR 11 policy the disk uses (`files/usr/lib/wolos/boot-keys`) or a TPM authorisation value checked by the TPM is the stronger form and is a later task |
| `fingerprint` | 32 random bytes sealed by the TPM like `tpm`, released by the daemon only after `fprintd` reports a match for this user | Needs a TPM; a biometric is never the only factor for export, move or a policy change (section 7) |
| `fido2` | `SHA-512("wolos/keyring/1/fido2", hmac-secret output)` of a security key, credential id and salt in the header (`fido2-assert -h`) | Works without a TPM; PIN and touch per the key's own policy |
| `recovery` | KDF(recovery code, salt): 26 characters of base32 = 128 bits, shown once when made | The way back when the TPM is cleared or the password forgotten |

Default policy at the first login: `{password}` and, with a TPM, `{tpm}` for the automatic unlock at sign-in (the login password still unlocks after the TPM is cleared), plus `{recovery}` once the person saves the code. Settings > Privacy & Security > Keyring enrols the rest.

### 4. Access control, like the macOS keychain
- Each item has an access list of applications allowed to read its secret without asking. The creator is on it. An application is identified by the kernel, never by the message (STANDARDS 1, ADR 0020): over the fast-path socket SO_PEERCRED and a pinned `/proc/<pid>` (`shared::sys::peer`, the same pattern as `api::peer::PeerIdentity`); over D-Bus the bus's `GetConnectionCredentials` (`ProcessFD` when the bus gives one, else the pid read once). The identity is the canonical executable path, its SHA-256, the systemd unit or scope (`app-<id>@…scope` names the desktop app, Flatpak's app id from its scope) and, when the executable belongs to a signed package, the package signer (ADR 0046).
- [state of the build] No shell sheet exists yet. Until it does, an application not on the list is **refused** (`denied`; the Secret Service answers AccessDenied), never granted; the owner puts a program on the list with `wol keyring acl allow EXE ATTR=VALUE` (the digest is taken at that moment) and takes it off with `acl revoke`. The creator of an item is on its list. An item no app is on the list of (imported, migrated or made at the terminal) is **owner-only**: only the owner at the command line reads it, apps are refused, and `wol keyring acl allow EXE` without attributes puts one program on the list of every item at once, `acl allow EXE ATTR=VALUE` on one item (each change is an `acl` audit line). An earlier draft granted such an item to the first app that read it; the Fable review (2026-11-04) found that a program that merely asks first gets a grant it was never shown, so it was removed until the shell's sheet exists. A binary that changes (an update of an unsigned package) asks again, which today means `acl allow` again; the signer rule below is what makes updates silent once packages are signed per ADR 0046.
- Target behaviour: an application not on the list gets a prompt (the shell's sheet: "Helium wants to use your saved password for example.com. Allow once / Always allow / Deny"); Always allow adds it to the list. Matching is by executable path and digest: an update that changes the binary of a signed package keeps the grant when the signer is the same, otherwise asks again.
- [fresh] Honest limit: on Linux a process of the same user may ptrace its own descendants (Yama `ptrace_scope=1`, ADR 0037 line 28), start an allowed app with preloaded code, or write into its files. The access list stops a script or a casual app from reading every secret; it does not stop malware that already runs as the person. Sandboxed apps (Flatpak) are identified reliably by their scope.
- The caller's identity is taken, and checked again, as follows [fresh, review finding 1]. On the fast path the process is pinned at `accept` (SO_PEERCRED pid, `/proc/<pid>` opened as a directory), and its executable path, the file's (device, inode, change time, length), its systemd scope and the SHA-256 of the file are read **before anything that can wait** (the digest cache has its own lock; the keyring's lock, which an unlock holds for the 100 ms of the KDF, is never taken to identify a caller). Every request compares the pinned process with that moment again and is refused if it executes another program, if its file was replaced, if it left its scope or if it ended, and the same check runs after the work, so a reply produced for a process that changed meanwhile is dropped, not sent. On D-Bus the pid is read from the bus, pinned, and the bus is asked again (a connection that still has that pid after the pin is the process pinned), and each call has the same before-and-after check. The window that remains is **fork and exec**: a process that connects, forks, and has the *parent* exec an allowed program keeps no allowed identity (the parent's request is refused after the exec; the child that kept the socket is identified by its own, unlisted, program), but between the last check and the moment the reply leaves the socket (microseconds) a process that executes another program with the descriptor open can still receive a reply meant for the earlier program. The access list is a defence against casual and accidental readers, not against a same-user attacker who can win that race; the section above states the same limit for ptrace and preload.
- Memory [fresh, review finding 4]: `wol-keyringd` clears `PR_SET_DUMPABLE` and `RLIMIT_CORE` at start (the program, not the library, which stays `forbid(unsafe_code)`), so another process of the same user cannot ptrace it or read its memory and a crash writes no core file (`tests/daemon.rs`, `the_daemon_keeps_its_memory_private`); `wolos-keyringd.service` adds `LimitCORE=0`. The password line of an unlock, the request and reply buffers of the fast path (including the base64 of a secret) are read into and written from buffers that are wiped when dropped. Not wiped, and so named: copies that serde, the `BufReader`s of the bus library and the D-Bus message bodies make on the way (a secret returned over D-Bus is a plain `Vec<u8>` in the message until the bus library frees it), and the kernel's socket buffers.
- Unlock back-off [fresh]: three wrong passwords are free, then the daemon refuses every try for 1, 2, 4 ... 30 seconds (`daemon::backoff`), so a same-user script cannot guess at the speed of the KDF; the KDF's own cost (Argon2id 64 MiB) is the second bound.
- Sign-in unlock [fresh]: at start the daemon opens the keyring only with the machine factor (the TPM device key) and only when the keyring has one; it never unlocks by TPM again after a lock, so locking is a real lock (the lock screen or `wol-login` unlock with the password over the fast path).
- Lock: on screen lock (the logind `Session.Lock` signal of the daemon's own session id, never another session's), on `PrepareForSleep` (lid close and suspend, logind) , after an idle timeout (default 15 minutes without a keyring read, settable, off allowed), and at sign-out. Locking wipes MK, `dek_wu` and the identity; `dek_afu` stays until sign-out, so `after-first-unlock` items keep working for the VPN while the screen is locked, and `when-unlocked` items do not.

### 5. Speed
- [fresh] While unlocked the daemon holds the decrypted metadata index in memory (attribute hash map, so a search is a lookup), each item's secret still sealed; a read derives the record key and opens one AEAD (a few microseconds), a write appends one record. There is no per-call D-Bus prompt round trip for an allowed app.
- Our own apps (the shell, `wol`, Atlas, NetworkManager's helper) use a Unix socket fast path, `$XDG_RUNTIME_DIR/wolos/keyring.sock`, one JSON line per request (read and write timeouts, maximum line, maximum count, STANDARDS 1 "IPC"); other apps keep the Secret Service on D-Bus.
- A memory-mapped index was considered and left out: a 10 000-item store is a few MB, read once at unlock; mmap would need `unsafe` or a new crate and would leave decrypted pages to the page cache rules instead of `zeroize`.
- [fresh] Two costs were taken off the read path after the first measurement (read p50 3.6 ms, dominated by the audit line's `fsync`): a read's audit line is appended at once but synced with the next durable line (`io::append_lazy`), and the signed checkpoint that falls due every 64 lines is signed by the daemon's timer (every 5 s), not inside a read. A power cut can lose the last few read lines; state changes (write, delete, import, export, acl, policy, unlock, lock) are synced before the call returns, so every change is audited durably and only the record that something was *read* in the last seconds before a power cut can be missing.
- Numbers: `docs/bench/keyring.md` (get, set, search; p50 and p99 over 10 000 items; ours in process, over the fast path and over D-Bus, gnome-keyring over D-Bus on the same box).

### 6. Audit
- Every unlock (and refused unlock), read, write, delete, export, import, move, access-list change and policy change appends one line to `~/.local/share/wolos/keyring/<name>.audit`: `{seq, time, event, app, item, result, prev}`, where `prev` is the SHA-512 chain value of the line before. The item is named by its random id, never by its label; the label is shown only when the keyring is unlocked.
- Checkpoints: at each unlock, lock and every 64 lines (signed by the daemon's timer when the 64th was a read), a line carrying the chain value, the line count and the store's record count and chain value, signed with the keyring's hybrid key (Ed25519 + ML-DSA-65, label `wolos/keyring/1/audit`). `wol keyring audit verify` checks the chain and every signature and reports the last signed checkpoint; lines after it are "not yet signed".
- What this does and does not prove [fresh, review finding 2]. The signing key is derived from a seed inside the block that the master key seals, so **anyone who holds the master key (the password, a recovery code, the unlocked daemon) can rewrite the whole log and sign it again**: the log is evidence against everyone who does not have the key (another user, a program that can only write the file, damage) and against edits in the middle of the log, not against the owner or against an attacker who has already unlocked the keyring. Rolling back is a separate problem: truncating `.audit` and restoring the `.wkr` to the same earlier boundary leaves two files that are each valid and agree with each other. The defence is a record kept outside both files: at every checkpoint the sequence number of the checkpoint and the store position (epoch, records) are written to `$XDG_STATE_HOME/wolos/keyring/<name>.state` (0600, a different folder from the data, so a backup or copy of the keyring folder does not carry it; the value never goes down). At open and at unlock the files are compared with it, `wol keyring` prints `WARNING` and `audit verify` fails when the log's last checkpoint is older or the store has fewer records, and the record is **not** advanced while a finding stands. `wol keyring audit accept` (after a legitimate restore from a backup) sets the record to the files as they are and audits that. What it still does not stop: an attacker of the same user who also edits or deletes the state file (it is a plain file) or who restores all three; the strong form is a monotonic counter in the TPM's NV area (an increment per checkpoint, which an offline copy cannot roll back), which is a later task named in the hand-back, not built here.
- Settings > Privacy & Security > Keyring shows the recent accesses grouped by app; `wol keyring audit` prints them.

### 7. Portability
- **Bundle `wolos/keyring-bundle/1`** (`wol keyring export FILE --to RECIPIENT` or `--passphrase`): the selected items (default: all except `this-device-only`), signed with the exporting keyring's hybrid key over `label "wolos/keyring/1/bundle" || header || payload` (sign inside the encryption, so the signer stays private and the signature binds the recipient), then encrypted either to the recipient's keyring identity (`wol keyring id` prints it: X25519 + ML-KEM-768, `wolcrypt::kem::seal`) or to a passphrase (KDF as section 3, at least 12 characters). The header (format, mode, recipient id or KDF parameters) is the AEAD's associated data. Import shows the signer's fingerprint, checks both halves of the signature and merges: an item with the same collection and attributes is replaced only when the imported one is newer.
- **Move** (`wol keyring move receive` on the new machine, `wol keyring move send HOST` on the old one, same LAN, no server): commit-then-reveal with a short authentication string, as Bluetooth numeric comparison. The receiver commits `C = SHA-512(fresh hybrid public key, 32 random bytes)`, the sender answers with its 32 random bytes, the receiver opens; both screens show the same 8-digit code (`SHA-512` of the transcript); the person confirms it matches on both; then the sender sends a bundle sealed to that fresh key with the transcript hash in its header. A man in the middle has one chance in 10^8 per attempt and nothing to compute offline; the code is all hash and hybrid KEM, so it holds against a quantum adversary. TCP on a port the receiver prints, 10-minute deadline, one transfer, then the socket closes.
- **Versioning and no downgrade**: every file starts with its format string; a reader accepts its own format and later minor additions it knows, refuses earlier formats except through `wol keyring migrate`, and never writes a classical-only form. A future `wolos/keyring/2` (for example ML-KEM-1024 or HQC) is read by a reader that also reads 1 and is written on the next compaction.
- **Migration from gnome-keyring** (`wol keyring migrate`, run once at the first sign-in after the update while gnome-keyring still owns `org.freedesktop.secrets` and has the login keyring open): read every item of every collection over the Secret Service, write them into the new store (access list empty: owner-only until the owner runs `wol keyring acl allow EXE`, or the shell's sheet exists), check the count, then stop gnome-keyring's secrets component and start `wol-keyringd` on the bus name. The old file is kept until the person deletes it in Settings, so a failed migration loses nothing. [state of the build] `wol keyring migrate` copies the items (label, attributes, secret) and changes nothing on the old side (it refuses when `wol-keyringd` itself owns the name, and when the old collection is locked); a second run replaces the same items instead of doubling them (same attributes); an item that cannot be copied is named and the command exits 1 so the old keyring is kept. Stopping gnome-keyring, renaming its file and enabling `wolos-keyringd.service` are image steps, not done here (see Build status).

### 8. Secret Service compatibility
`wol-keyringd` owns `org.freedesktop.secrets` with the subset our apps use (libsecret's `secret-tool`, Chromium/Helium, NetworkManager's agent): `Service.OpenSession` (`plain` only: on one machine's session bus the DH transport protects nothing the bus does not), `SearchItems`, `Unlock`, `Lock`, `GetSecrets`, `ReadAlias` (`default`, `login`), `CreateCollection` (refused politely: one collection, `login`), `Collection.CreateItem`, `SearchItems`, `Items`, `Item.GetSecret`, `SetSecret`, `Delete`, and the `Label`, `Attributes`, `Locked`, `Created`, `Modified` properties. Prompts go to the shell; when no shell answers, a request that needs one is refused, never granted. The lock screen and wol-login unlock through the fast path (`unlock` with the password), replacing `gnome-keyring-daemon --unlock` and the gnome-specific master-password call.

## Consequences
- Secrets of a stolen disk image need both halves broken for a bundle and the password KDF for the store: quantum-safe at rest and in transit.
- The browser and VPN keep working through the Secret Service; WolOS apps get faster through the socket.
- Out of scope: Secure Boot keys (firmware is RSA-only), the TPM's own internal RSA/ECC (a local chip boundary), Wi-Fi passwords (NetworkManager's store, may move in later as `after-first-unlock` items).
- Risks: an audit gap in the pure-Rust ML-KEM implementation (mitigated by the NIST and Go vectors in `crates/wolkeyring/tests/kat.rs` and the planned libcrux cross-check); the access list is a speed bump against same-user malware, as stated.
