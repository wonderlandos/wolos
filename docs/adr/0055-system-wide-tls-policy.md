# 0055 - System-wide TLS policy: post-quantum hybrid by default
Status: proposed (lead order 2026-11-04 20:50Z: "OUR TLS WILL BE ENTIRELY SECURE WE NEED TO PROTECT OUR USER FROM THE INTERNET WHEN WE CAN WITH POST-QUANT AND BEST WAYS"). Builds on 0040 (security defaults on Linux), 0042 (web runtime), 0052 (Federate, whose `wolcrypt::tls` group this reuses), 0054 (post-quantum keyring: one crypto implementation, `wolcrypt`). The CTO accepts it after review.

## Context
A computer that records today's traffic can decrypt it once a large quantum computer exists ("harvest now, decrypt later"). The key exchange is what must change now; certificates (signatures) only matter at the moment of the handshake, so they can wait for the Web PKI. The deployed answer is the hybrid group X25519MLKEM768 (codepoint 0x11EC, draft-ietf-tls-ecdhe-mlkem): X25519 and ML-KEM-768 (FIPS 203) together, so a break of either half alone reveals nothing. Chromium, Firefox, Cloudflare, Google and OpenSSL 3.5+ ship it on by default.

WolOS has several TLS stacks, and before this ADR each one did what its upstream default was. Measured on 2026-11-04 (forge, Arch at the image's snapshot 2026-10-31: openssl 3.6.5, gnutls 3.8.13, curl 8.23.0, nss 3.132, systemd 262.1) against pq.cloudflareresearch.com, federate.network and cdn.wolos.org, which all take the hybrid group:

Their content is signed end to end (pacman keys, ADR 0011), so the classical exchange there costs privacy of what was fetched, not integrity.

## Decision
One policy, every stack WolOS controls, values in one place (`wol_core::net`, `crates/core/src/net.rs`), each image file held to those values by a test:

1. **Key exchange.** X25519MLKEM768 first in every group list, X25519 right after it, then the NIST curves for old servers. ML-KEM is never offered alone (a flaw in a young implementation must not be the only protection), and a client never offers only classical groups when the stack has the hybrid one. Where the stack can send two key shares (OpenSSL `*` prefix, rustls hybrid component), it sends the hybrid and X25519 so a classical server costs no extra round trip.
2. **Versions and ciphers.** TLS 1.3 preferred, TLS 1.2 minimum. TLS 1.3 suites: AES-256-GCM, ChaCha20-Poly1305, AES-128-GCM. TLS 1.2: ECDHE with AES-GCM or ChaCha20-Poly1305 only (no CBC, no RSA key transport, no finite-field DH, no SHA-1 MAC). No renegotiation.
3. **Certificates.** Normal Web PKI verification through the system store everywhere (rustls-platform-verifier, OpenSSL's store); certificate transparency enforced in the browser (Chromium default; no exemption policy is ever written); OCSP stapling is used where the stack supports it (Chromium, OpenSSL clients that ask); HSTS preload in the browser (Chromium's list); the project's own site sends `Strict-Transport-Security` (its `_headers` file).
4. **Encrypted Client Hello** where the stack has it: the browser (on, pinned by policy) and the web runtime engine once its rustls provider carries HPKE (aws-lc-rs does; enabling ECH there needs the DNS HTTPS record lookup the engine does not do at the pin, a follow-up). OpenSSL gets ECH in 4.0; GnuTLS and rustls with ring have none.
5. **Session resumption.** Each stack's TLS 1.3 tickets as the server sets them (lifetime is the server's choice; clients do not keep tickets beyond it); 0-RTT early data is not turned on anywhere.
6. **DNS.** Names go through systemd-resolved; DNS over TLS is the Settings > Network choice (NET-3), which uses the system OpenSSL and so this policy. The browser's own DNS over HTTPS is pinned off (`DnsOverHttpsMode` = `off`): its automatic mode would send lookups to a public provider around the resolver and that choice.
7. **Readback.** `wol doctor tls` (`crates/controller/src/doctor/tls.rs`) connects to a post-quantum test server and to the update server with curl (OpenSSL), gnutls-cli (GnuTLS) and our Rust stack, says what each negotiated (version, group, cipher), a classical answer from the post-quantum server is a failure. It runs only when asked by name: it reaches servers outside the computer. The two checks that read files only, `security.tls-policy` (the marked lines are in both package files) and `security.browser-tls` (the browser policy has its rows), run in the always-run security area, so plain `wol doctor` and the Doctor app show a system that went classical (the script's exit-1 case). Settings > Privacy & Security > Connections says in one sentence per kind of connection what it uses (`crates/shell/src/copy_settings.rs`, `PRIVACY_CONNECTIONS`).

### How each stack gets it
- **OpenSSL.** Arch's `/etc/ssl/openssl.cnf` has no drop-in directory, so `files/usr/lib/wolos/tls-policy` adds two marked lines to it (`ssl_conf = wolos_ssl_conf` under `[openssl_init]` and an `.include` of `/usr/share/wolos/tls/openssl.cnf` at the end). The pacman hook `wolos-tls.hook` runs it after openssl, gnutls or the policy changes; `wolos-tls-remove.hook` runs `tls-policy --remove` before the policy is removed, so no `.include` is left pointing at a file that is gone. A file with an `ssl_conf` of its own is left alone and the script says so (exit 1). Programs that set their own groups or ciphers (curl `--curves`, a server's config) still decide for themselves.
- **GnuTLS.** The same script writes `default-priority-string` in an `[overrides]` section of `/etc/gnutls/config` from `files/usr/share/wolos/tls/gnutls.priority`. Programs that pass their own priority string instead of the default keep it.
- **curl.** Uses the system OpenSSL, so the OpenSSL policy; no curlrc change (our calls run `curl --disable` and the policy must not depend on a per-user file).
- **Our Rust (rustls).** One provider, `wol_core::net::tls_provider()` (core feature `tls`): ring's provider with wolcrypt's X25519MLKEM768 (`wolcrypt::tls`, ADR 0052: fips203 ML-KEM-768 and wolcrypt's X25519, the OS's one ML-KEM) first and offered for TLS 1.3 only, then X25519, P-256, P-384; AEAD suites only; TLS 1.3 and 1.2 (rustls has nothing older). Two helpers: `wol_core::net::agent_config()` starts every ureq agent (config builder with the TLS settings and the system's store) and `wol_core::net::tls_config(roots)` gives the `TlsConfig` to a caller that pins roots. `crates/shared/tests/rules_tls.rs` resolves each file's `use` items (aliases, `self`, groups) and fails when any other crate builds a `TlsConfig` or rustls `ClientConfig`, builds or installs a provider, touches its groups or suites, makes a ureq agent (`Agent::config_builder`, `new_with_defaults`, `new_with_config`) or sends an agent-less request (`ureq::get` and the other verbs), or glob-imports a TLS crate; and when a manifest names a second TLS library. Allowed: the helper, the engine shim, and federate's door (`source.rs`; `state.rs` takes random bytes from ring's provider). No aws-lc-rs in the workspace: a second, C, ML-KEM would be a second implementation to audit. wolcrypt's group does not yet give rustls its X25519 half (`hybrid_component`), so this stack sends one key share and a server without the hybrid group costs one HelloRetryRequest; adding it is a wolcrypt change (FEDERATE).
- **Web runtime engine.** The engine's own rustls is built with aws-lc-rs; the shim (`crates/webengine/src/engine/lib.rs`) installs that provider with X25519MLKEM768 moved first before the engine starts, instead of the engine's fallback default.
- **Browser.** Managed policy `/etc/atlas/policies/managed/wolos.json` (`wol_core::browser::tls_policies`, also written to the legacy `/etc/chromium/policies/managed/wolos.json` while the engine reads that path): `EncryptedClientHelloEnabled`, `BuiltInDnsClientEnabled`, `AdditionalDnsQueryTypesEnabled`, `HttpsUpgradesEnabled`, `DnsOverHttpsMode` = `off`. No launcher flag file may carry `--disable-ech`, `--disable-grease-tls` or `--ignore-certificate-errors` (test).
- **VPN.** WireGuard's handshake is classical. A peer `PresharedKey` mixes a symmetric secret into it, which a quantum attacker cannot recover from recorded traffic if the key itself was never sent over a classical channel; `nmcli connection import` keeps it. Rosenpass (packaged in Arch, `rosenpass` 0.2.2) rotates that key with a post-quantum handshake, but needs the same daemon on the server; WolOS does not ship it this round and the VPN page says how to use it with a provider that offers it.

## Consequences
- What cannot be post-quantum today, and why: servers that do not offer the hybrid group (the client cannot force it; it gets X25519); WireGuard without a preshared key; Flatpak and Steam runtimes (their own libraries and configs); certificates and signatures (the Web PKI has no post-quantum certificates yet; the handshake's authentication is classical, which is safe against recording but not against a future live attacker); UEFI and TPM-sealed keys (ADR 0054).
- TLS 1.0/1.1 servers and TLS 1.2 servers with only CBC or RSA key transport stop working for OpenSSL and GnuTLS programs. Measured: none of the project's own hosts, the Arch mirrors or GitHub are affected; an old router admin page may be.
- The two package config files carry a few marked lines; pacman keeps them (backup files) and the hook re-applies after upgrades. If the `/etc` overlay upper holds a copy (ADR 0044), later package changes to the rest of the file stay hidden, as for any edited `/etc` file.
- A stack's report in `wol doctor tls` is what it negotiated with two servers at that moment, not a proof for every site.
